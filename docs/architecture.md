# Architecture

PurityWallet retains Sparrow's JavaFX UI, Gradle build, Electrum / Core RPC adapters and wallet persistence architecture.
Application constants in `SparrowWallet` define the product identity. Internal Java package names remain compatible with upstream.

Purity checkpoints and ASERT header verification live in this project's `net` package and are used by `HeaderStore` and `ElectrumServer`.
The locked drongo and lark revisions are used as dependencies without modifying their sources.
Network presets use Bitcoin Purity services; application data and logs use independent `puritywallet` directories.

## Purity signet (REQ-012)

Startup and the restart menu share one supported-network list: mainnet, signet and development regtest. Existing per-network storage keeps signet configuration and wallets separate. The bundled signet peer uses TLS on port 60002; the explorer preset resolves to `/signet`, and transaction links avoid adding that path twice. Custom explorer templates and private connections remain supported.

`ChainCheckpoints` pins the shared signet parent at 327021 and requires the Purity activation block at 327022. Historical headers link to the existing shared checkpoints or the pinned parent. `PurityHeaderState` authenticates eleven seed headers (327011–327021) by linkage to that parent; the seed includes ASERT anchor 327017 and its parent timestamp. Signet uses its own PoW limit with the existing exact integer ASERT calculation, full MTP/future-time/PoW checks, activation pin and cumulative work. `headers/purity-signet-asert-v1` isolates the cache from the original Bitcoin signet profile. Public-server proof support is mandatory while verification is enabled; stored post-fork proofs are rechecked. Electrum and Core connections check the signet activation hash. Dependency sources remain unchanged.

Application and UI artwork comes from the local mobile PurityWallet project. JavaFX `ImageView` renders the canonical PNG in branded dialogs and wallet-model views; other wallet vendors retain their own SVG artwork.
Native icon containers include scaled versions of the existing transparent mobile logo at platform-specific sizes. See [Brand assets](branding.md) for provenance.

All project documentation is written in English.

The application, Gradle archives and native package metadata all use version `1.1.1`. jpackage uses the Gradle version directly; macOS bundle version fields use the same numeric value.

PR CI is one workflow, `.github/workflows/ci.yaml`, with `tests` (Linux, with Xvfb for JavaFX), `windows-installer` and `macos-dmg` jobs (REQ-015). It runs for PRs targeting master and pushes to master, with manual dispatch retained, and one build of a CI service that runs a single workflow covers every check. Tests use separate build-directory application homes. The Windows job builds and installs the unsigned MSI and checks its executable version. Each job also runs the JaCoCo coverage report for the `:test` suite, without the interface-only and hardware card driver packages, prints its line and branch coverage, and uploads it (REQ-016). Test reports and installer checksums are uploaded as CI artifacts; no release is published.

The `macos-dmg` job runs independently of the Windows job on a native `macos-15` runner and builds the Apple Silicon application with the pinned JDK; CI builds no Intel DMG. Gradle produces the app image; `hdiutil` wraps an ad hoc signed copy and an Applications shortcut in a compressed DMG. Mounted-image checks precede artifact upload. This job uses no Apple signing credentials and performs no notarization or release publication.

All GitHub packaging workflows, including the manual Package workflow, use credential-free ad hoc macOS signatures. Signing private keys, passwords and notarization credentials remain on the local signing machine and must not enter GitHub repositories, Secrets, logs or artifacts.

## Legacy-chain replay checks (REQ-011)
Mainnet and Purity signet share the application-owned legacy checks, UTXO status column/recheck button, Send input preview and signing/broadcast guard. Checks query transaction outputs and spent flags asynchronously through the configured HTTP proxy: mainnet uses `https://mempool.space/api`, while signet uses `https://mempool.space/signet/api`. A shared endpoint selector controls network eligibility, and each task captures its endpoint before background execution. Regtest and unsupported testnets make no requests. Results are transient and keyed by exact outpoints, values and scripts. UTXOs expose per-row state; Send checks the inputs of the constructed transaction, and the signing/broadcast guard runs a fresh check. Unknown results never imply replay protection. Cancelled requests and stale transaction snapshots cannot authorize an action. No wallet serialization or dependency source changes are needed.

## PWC provider (REQ-014)
The `com.sparrowwallet.sparrow.pwc` package connects the PWC Java Provider SDK (module `org.bitcoinpurity.pwc.provider`) to the wallet. `PwcService` creates the SDK `Provider` from the saved snapshot or afresh, starts the `LocalServer` endpoint under the network's provider id, and on stop saves the snapshot before closing the server and provider. `AppServices` starts it in desktop mode when the Settings switch is on and stops it on exit.

`PwcWalletBackend` implements the SDK `WalletBackend`. The SDK calls it serially on its own threads, never on the JavaFX thread. It reads the immutable `PwcView` that `AppPwcHost` publishes and never waits for the JavaFX thread (REQ-017). `PwcIds` derives opaque ids from output descriptors with a per-installation salt. `PwcEventForwarder` subscribes to wallet events and forwards them to `Provider.notify` from a single background executor.

`PwcPromptHandler` receives prompts on the SDK `pwc-prompts` thread and shows one JavaFX dialog per prompt. Dialogs poll for withdrawal, treat closing as rejection and answer the SDK exactly once. The replay acknowledgement, the password and the device confirmation follow the approval in the prompt flow, before the prompt is answered; an open prompt holds up no other request.

The snapshot and id salt live in `<data dir>/pwc/` with owner-only permissions. Packages exclude the SDK's bundled native libraries from the jlink image and copy only the current platform's `pwc_provider_jni` into the runtime `lib` directory; Windows launchers set `java.library.path` to that directory. On platforms without an SDK native library (Intel Macs) the first native call fails with a linkage error, which `PwcService` reports as "unavailable" without affecting other features.

## PWC backend without waits (REQ-017)
From SDK 0.2.1 the Provider calls the backend without its state lock, but still one method at a time, so a backend method that waits delays every Core request of every paired application. The design keeps each method to computation on data it owns plus, for `broadcast`, one bounded network call.

**Wallet data: an immutable view.** `AppPwcHost` subscribes to every event on the application `EventBus` and, coalescing bursts into one `Platform.runLater`, republishes a `PwcView` through a volatile field: for each open wallet form a deep copy of its wallet (copying the master wallet, so a child account and its master come from the same instant, and restoring the frozen status that `Wallet.copy` drops), whether it is locked or syncing, when it last synchronized and the wallet file time; and the connection state, block height, fee estimates, minimum relay fee and the two coin-selection settings. Reasons: a single snapshot is consistent across accounts and fields, which per-field thread-safe accessors on live models are not; nothing the JavaFX thread changes is read off it; and the existing backend logic (coin selection, signing) runs unchanged on `Wallet` copies. The cost is one copy of each open wallet, replaced (not accumulated) on each change, and staleness of at most one JavaFX event-queue turn after a change, which equals what a JavaFX-thread read would see once queued. Subscribing to every event rather than a list avoids a stale view after a missed event type. The backend derives its wallet and account entries (and ids) once per view and caches them with the view. The live `WalletForm` in the view is used only by code that runs on the JavaFX thread. This removes the `AppServices.isConnected()` call on a Provider thread that failed the Purity signet broadcast.

**Addresses.** `receiveAddress` and `createAddress` pick the first unused, unlabelled receive address of the view's copy that the backend has not handed out in this session; `createAddress` then labels it and extends the gap limit on the live wallet through `Platform.runLater`, without waiting. The handed-out set keeps two requests from receiving the same address before the label reaches the view.

**Replay check and acknowledgement.** They run once, in the PSBT prompt flow after the user approves (as before), not in `broadcast`, which has no prompt and would hold up all applications. When the check finds no shared input, or the user acknowledges a shared or unknown result, and the prompt is then approved, the handler records a clearance for the transaction. The clearance is matched to the broadcast by the transaction's version, lock time, input outpoints with sequences and outputs: these are fixed when the PSBT is signed, unlike the txid, which changes when a non-SegWit input of another signer is finalized, while a different spend of the same inputs does not match. It is valid for 30 minutes, long enough for a Client to finalize and broadcast, and is consumed by a successful broadcast, so a failed broadcast can be retried. A check result that changes after the acknowledgement does not matter: the acknowledgement already accepted the worst case (shared), and a coin can only leave the legacy UTXO set, not enter it. A broadcast on mainnet or Purity signet without a clearance (signed or combined elsewhere, expired, or never checked) is refused at once with `POLICY_VIOLATION`, the Core code for a request this wallet's policy forbids, rather than `USER_REJECTED`, since the user was never asked; no dialog opens and no network request is made. The user can broadcast such a transaction from the wallet UI, where REQ-011 applies. Regtest needs no clearance.

**Hardware signatures.** After the approval and replay check, the PSBT prompt flow opens the existing `DeviceSignDialog` for USB hardware accounts and waits there, on the prompt thread, not in a backend call. The returned PSBT is checked with `verifyCombinedSignatures` and kept with the account, the exact PSBT bytes and the inputs to sign; only then is the prompt approved. The SDK passes the same PSBT bytes to `signPsbt`, which takes the kept signatures once, checks them again and copies those of the requested inputs. A withdrawn or expired prompt closes the device dialog and nothing is kept; cancelling, or an unplugged device (the dialog reports the error and the user closes it), rejects the prompt with `USER_REJECTED`. A missing, mismatched or expired device signature in `signPsbt` is `SIGNER_UNAVAILABLE`.

**Kept approvals.** Decrypted wallets and device signatures are kept by account with the subject of the approval: the exact PSBT bytes and inputs to sign, or the message, address and format. A backend call takes the approval for its account; it is used only when the subject matches and it is less than 2 minutes old (the SDK calls the backend as soon as the prompt is approved), and is removed either way. Decrypted keys are cleared after the signature, on mismatch, expiry or withdrawal, and when an approval is replaced.

**Timeouts and errors.** `broadcast` is the only backend method that uses the network. It runs the Electrum broadcast on a daemon thread and waits at most 30 seconds, longer than the Electrum transport's first read timeouts, so a slow but working server answers. A timeout or a transport failure is `NETWORK_UNAVAILABLE` (the transaction may still arrive; a retry is harmless), an error answer from the server or a different txid is `TRANSACTION_REJECTED`, and the result is the transaction's own txid in display order. Every backend method is wrapped: a `PwcException` passes through, anything else is logged and becomes `INTERNAL_ERROR`, or an empty answer for the methods that declare no error.

**Host calls on the JavaFX thread.** The Settings page and `PwcService` keep calling `pairedClients`, `grants`, `revokeGrant`, `unpairClient` and `saveState` on the JavaFX thread: from 0.2.1 these no longer wait for backend calls. `Provider.notify` stays on the `pwc-events` executor, which costs nothing and keeps the subscribers trivial. Stopping the provider may wait for the backend call in progress, which is now bounded by the 30-second broadcast limit.
